# Native C++ prototype reuse audit

Checked 2026-10-12 against the copied prototype source in [`port/spikes/training-native-prototype/`](../port/spikes/training-native-prototype/README.md) and the active MBase map inventory. The prototype is a substantial gameplay reconstruction, not just a renderer demo: `main.cpp` wires movement, collision, tools, fire contacts/suppression, victims, doors, authored script events, actor drawing, and a frame loop. Its current build compiles that integration as one large translation unit. The user reports having reached gameplay in the prior setup; this shell has verified compilation and local asset resolution, but could not create a display to verify interactive launch.

## Reuse decision

Reuse source-backed mechanics directly where their inputs match. Do not rewrite those behaviors from scratch. Replace or generalize the level bootstrap and data adapters so MBase drives the same components. Keep the existing Training executable as a gameplay reference until the shared runtime can load a rescue map.

The generated scene data is local and must be regenerated for another BSP. |

The MBase overlap is substantial: its BSP includes a rescue player, fires, victims, bounds triggers, BModels, PropModels, and EscapeArrow entities. That aligns with many gameplay systems already present in the prototype. It does not yet prove that the Training host creates MBase actors correctly or that the current geometry exporter can produce MBase data.

## Integration path

1. Preserve the current Training workbench as the existing gameplay reference; the current shell has only verified its build and local asset resolution.
2. Extract reusable gameplay headers behind a shared runtime interface without changing their recovered ordering or floating-point behavior.
3. Build a general BSP/resource exporter and a catalog-selected `SceneData` input. Feed MBase into the existing fire, victim, interaction, script, and actor components.
4. Move game startup, controls, and rendering behind platform-neutral services. Replace CoreText/CoreGraphics UI and the fixed Training asset path as part of the shared desktop runtime.
5. Compare the MBase path against its authored entities and the pinned EXE before adding a second rescue mission.

No component is approved as behavior-complete solely because the Training prototype rendered or played it. For each promoted component, retain its binary hash, source trace, data assumptions, and a scenario comparison. The separate [legacy review](LEGACY_WORK_REVIEW.md) records how prior Ghidra evidence and the BSP entity reader were carried forward.
