## Contact-list admission and producer

- Common root initialization `0049D420` sets root `+0x14` admission mask to `0xFFEB`, root type `+0x18` to 0, and category mask `+0x20` to 0. PropModel constructor `00444A40` calls `0049D330(this,1)`, which sets category bit 1 (`0x2`), and does not overwrite root `+0x18`. Therefore a PropModel instance registers in contact-manager type list 0 and advertises that it checks type list 1.
- `00429490` routes roots whose `+0x14` mask intersects manager filter `0x20` to the contact manager at owner `+0xE0`. PropModel's `0xFFEB` includes this bit. `0049BC90` selects the contact list from root `+0x18` as `((type+1)*0x48)` relative to the manager, then appends to its active list. The contact pass `0049BD20` iterates the PropModel's category bit 1 and dispatches root slot `+0x48` against list 1. The authored Training Player has root type 1; thus it is the authored candidate class for PropModel touch checks (dynamic additions to type 1 are a separate possibility).
- Primary PropModel vtable is `004E1390`. Its `+0x48` word at `004E13D8` is `00443700`. The pinned executable bytes show `00443700` as the candidate producer: it checks the PropModel model's enabled byte, calls candidate root slot `+0x0C` for a world-space point, compares squared point distance against the PropModel's authored touch radius, applies the `0048FE20` world-leaf visibility predicate at the PropModel position, builds the candidate key through `0049D350`, and inserts the pair into PropModel root `+0x158` through `004901E0`. Constructor `00444A40` initializes this pair container with capacity 16. This identifies the PropModel's own producer; it does not rely on BoundsTrigger code.
- The first gate in `00443700` reads byte `+0x45` of the model object at PropModel root `+0xD0`. `00443860` creates/loads the model through `00497E90`; that initializer explicitly writes model byte `+0x45 = 1` (also `+0x44 = 1`, `+0x46 = 0`). The normal successfully initialized PropModel therefore enters candidate checks with the tested enable byte set. This states constructor/setup initialization only; later model lifecycle code could change the byte.
- `setscale` is a replacement. PropModel command handler `004444B0` parses three floats and calls `004437C0`; that setter passes them to `0042D280`, which stores the three values directly at the model transform's `+0x34/+0x38/+0x3C` and copies them to its return vector. It does not multiply by the current scale. `00497E90` initializes that triplet to `(1,1,1)`, and `00443860` also sets `(1,1,1)` during setup, so Training `ext1`'s `setscale 0.2 0.2 0.2` replaces unit scale with `(0.2,0.2,0.2)`.
- The authored Training Player primary vtable is `004E1C48`; slot `+0x0C` is thunk `0049DB90`, which jumps to `0049D790`. The getter resolves the entity transform at root `+0x24`, obtains its world point through `00496020`, stores that point at root `+0x68`, and returns the `+0x68` point pointer. Thus the PropModel overlap distance compares the PropModel center at root `+0x4C` to the Player's returned world-space point, using the radius at the PropModel user-data `+0x20` field.
- `0048FE20` takes a world/scene object and a point; selects the world pointer from scene-object `+0x78` via either `+0xB4` or `+0x08` depending on byte `+0x160`; calls `geWorld_GetLeaf` for the supplied point and then `geWorld_MightSeeLeaf` for that leaf. The PropModel caller supplies the current world/scene object from the global context and the PropModel center. It is a leaf visibility gate after the radius comparison, not part of the distance calculation.

## Contact-event drain and scheduling boundary

- Primary vtable slot `+0x14` at `004E13A4` is `00443580`. The pinned bytes show this callback invokes `UpdateScriptActorWaitAndQueue` (`00470740`) on the PropModel subobject at root `+0xD4`. That shared routine calls the subobject vtable slot 0 when its script wait is not active; PropModel's `+0xD4` vtable `004E1388` slot 0 is `00444050`.
- `00444050` is the PropModel-specific contact-event drain. It passes the contact-pair container at root `+0x158` to shared contact event dispatch `00470840` (with the companion pointer computed at root `+0x170`). The routine then copies the current pairs through `00490430` and clears the current list through `0043AED0`. Its separate nonempty/empty branches perform their own contact-state/selection handling (`00490300`/`004903A0`, `00459050`/`00459090`); no claim about their user-visible effect is needed to identify the drain. Shared `00470840` maps pair deltas to the ScriptActor contact event vocabulary (`touch`, `touching`, `untouch`).
- The producer path is scheduled by owner contact-manager passes: `0042AEA0 → 00429520 → owner +0xE0 → 0049BD20 → PropModel slot +0x48`. This is once per normal invocation of that owner pass, not a proven wall-clock/frame rate; `0042AEA0` has an early branch that bypasses the normal manager pass.
- The event drain is reached only when PropModel primary slot `+0x14` runs. The path is now verified locally as `root +0x14 (00443580) → 00470740 → subobject slot 0 (00444050) → 00470840`, but its external recurring caller and ordering relative to `0049BD20` are not established. A bounded raw-binary scan found no direct call instruction to `00443580`; this does not rule out an indirect dispatcher. Therefore same-pass vs later-pass delivery, event latency, and wall-clock cadence remain unresolved. Do not equate slot `+0x14` with a known global update schedule.
