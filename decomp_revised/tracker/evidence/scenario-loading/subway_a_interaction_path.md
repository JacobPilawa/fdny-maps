## Static code route

The event binding is not a special Subway-only code path. It uses the shared
ScriptActor parser and contact machinery:

1. The map EVS `set` statements store `brokendoor` and `subdoor` in the shared
   script-variable table. Each BSP `S_Script` property references a variable
   with `*name` syntax.
2. BModel initialization (`InitializeBModelEntity`, `0043C670`) and BoundsTrigger
   initialization (`InitializeBoundsTriggerEntity`, `00441040`) send each
   nonempty script property through `DispatchScriptActorCommandWithContext`
   (`00475310`). `ParseScriptActorCommandText` (`00474180`) expands `*name`.
3. The parser turns a colon event declaration such as `touch:` into the internal
   `onmsgappend` command. `HandleCommonScriptActorCommand` (`0046F9D0`) records
   that event in the ScriptActor table at `+0x08` through
   `AppendScriptActorEventCommands` (`0046F820`). The semicolon form uses
   `SetScriptActorEventCommands` (`0046F6F0`) and replaces the event's command
   list. `DispatchScriptActorEvent` (`004705B0`) later looks up an event key and
   routes its associated command list.
4. BModel contact candidates reach `CheckBModelContactCandidate` (`0043B620`);
   `UpdateBModelEntity` (`0043DC60`) converts its pair changes into ScriptActor
   events. BoundsTrigger candidates reach `CheckBoundsTriggerContact`
   (`00440CE0`), and `DispatchBoundsTriggerContactEvents` (`00440DC0`) uses the
   same `DispatchScriptActorContactEvents` converter (`00470840`). New, kept,
   and removed pairs map to `touch`, `touching`, and `untouch`.
5. On `subdoor` touch, the BModel command handler (`0043E680`) applies time
   scale 4, routes `playsnd SubDoor`, and sets the opening state. Its update
   advances each child Genesis motion path and the authored transform. On
   `untouch`, the script routes the same sound command and sets the closing
   state. The `brokendoor` touch handler routes `playsnd Zapp3d`.

The shared `playsnd` command branch is in `0047A1F0` and calls
`HandlePlaySoundCommand` (`00477AF0`). It reads the executing ScriptActor name
from `+0x24`, resolves that name through the shared registry, samples the
registered actor's geometry position, and submits the sound string and source
position to `GetOrCreateSpatialSoundInstance` (`004749A0`) in manager
`DAT_00503060`. Thus Subway A's `SubDoor` instances are statically anchored to
their named door actors, and each `Zapp3d` touch sound is anchored to its
named BoundsTrigger actor. The special `<console>` origin resolves to `player`.
`GetOrCreateSpatialSoundInstance` stores the resource name, source position,
owner, and game-clock time. `ResolveSoundResourceByName` performs a named
resource-tree lookup. `DispatchOrQueueSoundPlayback` starts the resolved sample
or stream through `StartFMODSampleOrStream`, applies volume, updates 3D
attributes when the resource flag is enabled, and unpauses the channel. The
spatial update reaches FMOD's `FSOUND_3D_SetAttributes` through
`SetFMOD3DAttributes`.

## Sound resource join

The hash-pinned `Data/ResDefs/sound.rrf` declares both event sounds as
`ROC_SOUND_BUFFER3D` entries with the authored numeric values `200 1000`:

| Script name | Resource definition | Audio file | SHA-256 |
|---|---|---|---|
| `SubDoor` | line 153: `ROC_SOUND_BUFFER3D SubDoor 200 1000` | `Data/Snd/subdoor.wav` | `2d5259e3c8818a01e7e57d8b039dd2347e03cb05a3a9608bba18be3ca51d337e` |
| `Zapp3d` | line 119: `ROC_SOUND_BUFFER3D Zapp3d 200 1000` | `Data/Snd/spark1.wav` | `7a23bd198f920cabc9365a37bf04d0a820aa0eda7a086f002a63d17305ee55f4` |

The EXE's resource-definition parser confirms the complete static mapping.
`LoadResourceDefinitionsFile` distinguishes `ROC_SOUND_BUFFER2D` from
`ROC_SOUND_BUFFER3D` and passes a type byte of 0 or 1 to
`ParseSoundBufferDefinition`. The parser reads the two numeric values only for
3D buffers, then passes the type byte to `FindOrCreateSoundResourceByName`.
`InitializeFMODSoundResource` stores that byte at resource offset `+9` for WAV
samples; `DispatchOrQueueSoundPlayback` copies it to the sound instance, where
`UpdateSound3DAttributes` gates the FMOD 3D call. Both Subway sounds are WAV
samples, so the 3D flag is enabled for these definitions.

`SetFMODSampleMinMaxDistance` forwards the first and second parsed values, in
order, to `FSOUND_Sample_SetMinMaxDistance`. Thus both Subway entries configure
minimum distance 200 and maximum distance 1000. The generic script `playsnd`
route supplies a null optional playback value, so when the sound is played the
3D updater forwards the stored actor coordinates directly; its separate
value-2 branch is not selected.

The parser type callsites and min/max argument order are captured in
[`sound_rrf_type_and_distance_assembly.md`](sound_rrf_type_and_distance_assembly.md).

## Limits and next capture

This closes the static Subway A binding and handler route for the automatic
doors and broken-door touch cue, through sound-resource lookup and the FMOD
playback/3D-attribute APIs. It does not prove the triggers overlap in a
particular playthrough, the update order or cadence, the perceived opening
speed, the audible falloff on a target platform, or visual parity. Those remain
open; the authored coordinates above provide concrete probe locations
for a future Wine/Sikarugir or Windows capture. This is one part of Subway A's
rescue scope, not evidence that the mission or port is complete.
