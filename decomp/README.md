# FDNY Training — C++ reconstruction

A native Mac reconstruction of the original executable's Training mode, map and scripts. This folder is the working copy; the public GitHub mirror omits local retail inputs and raw reverse-engineering exports.

Implementation roadmap: [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md).

Start here: [HANDOFF.md](HANDOFF.md) for the current verified snapshot, then [CHECKLIST.md](CHECKLIST.md) for detailed progress. Update the checklist whenever implementation, verification or outstanding work changes.

Training progress report: [training-progress.html](training-progress.html). It uses a file tree and labeled original-code blocks to show component comparisons, integration state and evidence without a guessed decompilation percentage.

## Public GitHub copy

The `decomp/` folder in the parent repository preserves native source, analysis tools, concise findings, numeric oracle fixtures, the checklist and progress viewer. `.gitignore` keeps the original executable, DLL and BSP, extracted retail assets, Ghidra databases, raw machine-code/decompiler exports, local debugger captures, build products and bundled Unicorn binaries in this working directory. Those local files remain untouched. A public clone therefore needs the user's own Training assets and local Unicorn runtime to run the app and oracle scripts; the included C++ source and documentation remain available independently.

## Scope and preservation

Training is the immediate playable target. Shared engine and gameplay routines are recovered as reusable components so later maps can use them. The local workspace retains original code exports, assembly, assets and comparisons, including variants and work outside Training; the public mirror includes authored notes and numeric comparisons. `evidence/function-index.json` indexes the local native exports by address and content hash; regenerate it with `python3 tools/index_evidence.py`. An indexed function is evidence, not a claim that it has been fully understood or ported. `mechanics.json` tracks implementation and verification separately from live integration.

## Run

```sh
./run.sh
```

Build dependencies: CMake, a C++17 compiler, SDL2 and json-c. On a Mac with Homebrew: `brew install cmake pkg-config sdl2 json-c`.

WASD moves, the mouse looks, right mouse or Space jumps, C or either Ctrl key toggles crouching, and 1/2 select the equipped axe/extinguisher (keypad 1/2 also work). When the extinguisher is selected, left mouse enters its recovered action state and drives live contact sampling, queued suppression and source-backed effect timer/offset draws. After attaching Hose Spray at a valve, left mouse updates its source-backed active byte and effect deadline; hose stream contacts, sound and presentation are not connected. Original player/owner callback timing, particle presentation and visible fire lifecycle remain unfinished. Esc releases the mouse. Close the window to quit.

## Matching the original RNG

The game has one shared random-number stream. Fires, victims, footsteps, sounds and effects draw from it. Matching a seed also requires matching every draw in its original order.

The C++ generator matches 20,000 original float results, 4,000 victim spawn-index conversions and 16,000 mixed integer/float operations. The original sound-choice routine also matches across 3,000 cases, including its extra draw when it avoids repeating a sound. These comparisons execute the original executable's instructions.

The fire-effect initializer now matches 1,140 original calls, including smoke delay, all four sprite speeds and starting frames, draw counts and repeated initialization. Victim beckon timing and sound selection match another 9,000 original updates, including timer wrap and repeat avoidance. The initial victim sound deadline also matches 114 original constructor captures, including RNG reload boundaries. `0045B690` constructs the victim sound controller before choosing the first ACT motion, so the native first pass now stores that 0–5,000 ms deadline and previous-sound index before the motion draw. Victim beckoning and playback remain unintegrated.

The assembly shows that victim sound delays are converted from seconds to milliseconds and added to the current game time. The decompiled text omitted those operations. Looping sounds consume another random draw when playback actually starts; queued playback delays that draw. Level loading pauses sound requests. Fire effects and FireBurn sound choices run before victim spawn selection, while the queued loop phases draw when playback resumes afterward. The sound queue matches 24 original-machine-code replays, including duplicate requests. The volume-setting function immediately before the queue resumes (00429BA0) sets sound-group volumes; it does not choose random values.

Startup groups entities by class. It constructs the whole batch, initializes every entity, then runs a second initialization pass. Requests added by a constructor join the current batch; requests added during either initialization pass wait for the next batch. The C++ dispatcher matches four original-machine-code scenarios (72 event/count comparisons), including additions in each pass and an empty request that ends a batch. Script startup now uses this dispatcher; full entity constructors and initialization are still being integrated. The original World entity enqueues BSP entities during its first initialization pass. Its constructor sets a four-update countdown; at zero, its update routine (0049E2C0) calls 00471310 with the world filename and sets the main state field to 3. The playable build now loads only top-level set/exec lines before entity scripts, then runs the full level script after four world updates. The countdown and completion/state transition match 120 original updates. Full entity scheduling and the original loading-state transitions are still being integrated. Victim alternate points register before the second pass chooses their spawn. Training has two victims; each has three possible starting points, with the editor location first.

The original clock matches across 3,000 recorded updates, including its stored float bits, pauses, waits, long frames and timer wrap. ARM's normal double arithmetic produced a one-millisecond difference in one case; the port now preserves the original x87 arithmetic for this calculation.

The full 624-word RNG state can also be saved and restored. Eighty-eight original captures, including reload boundaries, match 66,176 state/output comparisons. The generator and these individual routines are verified. Full Training RNG parity still requires connecting all gameplay, sound and effect routines and comparing a complete original run. The current playable build does not yet include those systems.

## What will count as complete

A matching generator alone is not a matching game. The final comparison must start from the same original RNG state and use the same input and frame timing. It must match each random draw in order, the victim spawn and movement decisions, and the fire creation, growth, spread, suppression and damage events. Startup, sound playback, effects, script queues and entity updates must consume their original draws at their original points. Missing consumers must be implemented rather than compensated for by discarding guessed numbers.

The fire-effect comparison executes the original initializer and constructors, with a fixture allocator and a null world to avoid engine registration. The victim-sound comparison executes the original update with the final playback callback replaced. Their resource fixtures test the routines; a complete Training run remains the final check.
