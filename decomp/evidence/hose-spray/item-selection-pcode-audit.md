# Hose Spray item-selection transaction audit

Date: 2026-10-12

## Training inventory facts

The item pointer array begins at `Player+0x3564`; its count is `Player+0x3568`, and its selected zero-based index is `Player+0x357C`. Training entity 115's `equip axe` command flows through EVS handler `00451870` to `0044D080`. Name lookup `0044CA50` maps axe to kind 1; the factory allocates `0xA94` bytes, invokes constructor `00460A50`, stores the item at slot 1, then calls `0044C2A0(Player,1,false)`. The axe constructor installs vtable `004E2868`. The selection helper activates slot 1 when the prior selection is zero.

Training's `touchhose 25` command reaches `0044CAB0`; Hose Spray is stored at slot 4 and starts in mode 2 at item `+0xC68`. The command does not select it. This proves the Training slots used by the new native indexed inventory adapter: axe 1 and hose 4. It does not establish axe's full action behavior or any other game's inventory layout.

## Owner transaction behavior

`0044C840(Player,valveRoot,action)` first checks the expected five-slot array and reads Hose Spray from slot 4. Action 1002 calls `00463370(hose,2)`, then `0044C360`, then hides the item UI at `Player+0x4C0`. Other action codes take the attach branch. With a non-null Hose Spray, attachment selection behaves as follows:

- Current slot 4: keep selection and proceed to frame construction.
- Current slot 0: write selected index 4, call hose `+0x3C(1)`, then refresh HUD.
- Any other selection: call its vtable `+0x38()`; false hides UI at `Player+0x508` and returns; true calls old item `+0x3C(0)`, writes slot 4, calls hose `+0x3C(1)`, and refreshes HUD.

`0044C360` scans populated slots from zero upward and delegates to `0044C2A0(Player,index,true)`. Forced reselection bypasses the old item's `+0x38` gate. The first populated slot succeeds; if selection changes, old `+0x3C(0)` runs before the selected-index write/new `+0x3C(1)`, followed by HUD mode 5. If none are populated, it writes selected index zero. The final owner path hides UI at `Player+0x4C0`.

Mode setter `00463370` writes `item+0xC68` only when changed. Transitions out of 0/1 into 2/3 call HUD mode 6 with parameter 4; other changes call mode 5 with a null parameter. Detach from mode 3 to 2 therefore emits HUD mode 5 before the first-available rescan. Detach does not clear the saved valve pointer `item+0xC6C`; mode 2 makes that stale pointer irrelevant to candidate action selection until a later attachment overwrites it.

## Original execution comparison

`tools/ghidra/HoseItemSelectionPcodeOracle.java` runs the hash-pinned PE32 through `0044C840`, `0044C360`, `0044C2A0`, and the real `00463370` setter. The actual array helpers and scan logic execute. The Axe item's `+0x38` call is a controlled boundary whose return is calculated from the source-mapped `0045F930 → 0045FA50` field formula; Ghidra has no instruction listing at `0045FA50`, so those two leaf methods are not claimed as executed P-code. Other item `+0x38/+0x3C` calls, HUD `004571A0`, and hide `004A11A0` remain controlled service boundaries. Attach samples stop at `004977B0`, after selection and HUD refresh but before valve-frame math or the pointer/mode-3 stores.

The owner cases cover slot-0 direct switch, idle/blocked Training Axe switch, an enabled busy primary child, already-selected Hose Spray, missing Hose Spray, first populated detach target, first target already selected, and mode-2 detach. The Axe gate cases supply source fields `+0x1FC`, `+0x568`, and `+0x9B0` to the controlled boundary; they are test inputs, not values captured by original P-code. A separate `0044C360` case checks the no-candidate selected-index clear. The fixture compares selected index, inventory slots, hose mode, saved-pointer state and the ordered boundary-event sequence. `hose_item_selection_pcode-check` compares the owner transaction and its callback ordering with the original execution under that explicit gate adapter.

The Axe gate's initialized value is source-established. Factory `0044D080` constructs it with `00460A50`, then calls its vtable `+0x08` initializer `0045F970`. That initializer dispatches `+0x08` on both Axe subobjects; their `004E27F0+0x08` entry is `00460250`, which sets the receiving subobject's `+0x368` to zero. For the child at Axe `+0x648`, that is Axe `+0x9B0`. The root gate `0045F930` queries the first child only when Axe `+0x1FC` is nonzero, then always queries the second child; each child method `0045FA50` returns true exactly when its own `+0x368` word is zero. Native `AxeSwitchGate` preserves this short circuit and uses source fields `+0x1FC/+0x568/+0x9B0` for Training slot 1. The controlled owner-oracle adapter covers idle, secondary-busy, disabled-primary-busy (the nonzero primary state is ignored), and enabled-primary-busy inputs; the native Training scenario separately checks the busy value 3 blocks the Hose attach. The address-matched local Ghidra body is backed by the original executable hash above; independently, `objdump -D -Mintel --start-address=0x45fa50 --stop-address=0x45fa80 evidence/original/FDNYFirefighter.exe` yields `mov edx,[ecx+0x368]; xor eax,eax; test edx,edx; sete al; ret`. Ghidra's preserved project has no instruction listing at `0045FA50`, so a direct EmulatorHelper execution of this leaf is still open. The values are stateful: updater `0045FAD0` clears `DAT_00502E04`, dispatches child `+0x18` updates, then writes `Axe+0x9B0=3` if a child raises that flag. The successful hit path in `00460B90` raises it; handler `00461120` reaches that path when the child state at `+0x368` is 1. Child animation/update paths later change and clear their state. Runtime Axe hit/action dispatch and updater cadence remain open, so the native Training loop currently stays at the constructor-established idle state unless a caller supplies later field values. Reviewed local Ghidra bodies are retained under `evidence/tool-decompiled/0045f930_FUN_0045f930.c`, `0045fa50_FUN_0045fa50.c`, `0045f970_FUN_0045f970.c`, `00460250_FUN_00460250.c`, and `0045fad0_FUN_0045fad0.c`; `evidence/function-index.json` preserves their original-executable hash associations.

The Axe activation callback is also resolved. Vtable `004E2868+0x3C` points to `0045F9B0`; it calls `0045F620(this,active)`, then conditionally forwards `+0x3C(active)` to the `+0x200` child and always forwards to the `+0x648` child. `0045F620` writes the Axe active byte at `+0x158`, calls the item animation service, and on activation reattaches its follower to Player frame `+0x34A4`. Both child `+0x3C` entries reach `0045FA30`; its shared activation logic sets the child active state, and deactivation also clears Player byte `+0x345C`. The animation service internals and original frame scheduling remain separate work.

## Source-mapped attachment frame commit

After successful Hose Spray selection, `0044C840` resolves the valve root's local frame at `valve+0xD0` through `004977B0`. The resolver follows parent pointers at frame `+0x40`, composes each parent with `00497300`, and finishes with frame copy `0042D0A0`. Correction from owner-level P-code: `00446EE0` copies the first basis vector at resolved-frame `+4..+0xC`, not the translation at `+0x28`; `0042D2B0` negates its three components. The resulting negated axis is stored at Hose Spray `+0xC7C..+0xC84`.

The owner then calls the valve root's vtable `+0x18` to obtain a frame-like object and copies its `+0x28` three-word position into Hose Spray `+0xC70..+0xC78`. It stores the valve-root pointer at Hose Spray `+0xC6C`, switches to mode 3 with `00463370`, then reads the first generated stream-pose node through the list head at Hose Spray `+0xCB8`, caches that node pointer at `+0xCD0`, and copies the position from `+0xC70..+0xC78` into node `+8/+0xC/+0x10`. The owner then hides the item UI at Player `+0x4C0`.

`tools/ghidra/HoseAttachmentFramePcodeOracle.java` runs the original `0044C840` owner through `004977B0`, `00446EE0`, `0042D2B0`, the controlled valve `+0x18` getter, mode setter, and first pose-node write. Six frame trees (four controlled plus the two Training valve matrices from the companion frame oracle) compare three Hose vectors (54 words), mode, saved identities, and ordered HUD/hide calls in the saved fixture. The focused native comparison (`ctest -R '^hose_attachment_frame_pcode$'`) passes 1/1 and covers all six fixtures; the two Training matrices still inherit the companion oracle's Java `Math` substitution for x87 `FCOS`/`FSIN`, so residual basis/offset words are not hardware-confirmed. It establishes the source angle words (`-360°`, `-180°`, and `-0° pitch`) and exact authored positions. Native comparison: `src/hose_attachment_frame.h` and `tools/hose_attachment_frame_pcode_check.cpp`.

### Training valve frame inputs

Training Valve3 (entity 159) and Valve5 (entity 164) both use `D_Model=5`, `E_Pitch=0`, touch radius 70, and `S_Script01=makevalve`. Their authored headings are 9° and 3°; their `ZZ_location` values are `(1368,-176,-2080)` and `(416,-176,-2404)`. PropModel constructor `00444A40` copies `ZZ_location` from UserData `+4/+8/+0xC` into its embedded frame at PropModel `+0x4C/+0x50/+0x54`. The main vtable is `004E1390`; slot `+0x18` reaches `0049D760`, whose two branches return `PropModel+0x24` or null. Thus the getter result `+0x28` is the authored position consumed by the owner and written to Hose `+0xC70`.

The same constructor's base setup allocates a 0x100-byte model frame object at PropModel `+0xD0` and initializes its parent link to the embedded frame at PropModel `+0x24`. Setup callback `00443860` is PropModel vtable slot `+0x20`; it loads model 5, sets unit scale, converts authored heading/pitch, and rotates through `004968B0` and `00496B50`. Actor ID 5 is `valve.act`, with one identity root-bone attachment and no motions. Original x86 instructions convert Training headings 9°/3° to `-360°`/`-180°`; pitch becomes `-0.0f`. The rotation oracle executes those instructions but substitutes Java `Math` for Ghidra's unsupported x87 `FCOS`/`FSIN`, so final residual axis words remain provisional. The companion owner fixture runs both captured matrices through the original `0044C840` commit, with offsets recorded in `valve-actor-resource-audit.md`. The Training factory/entity-set/FIFO trace places this setup ahead of the Player's staged initialization on a normal successful level load; no live callback trace or recurring PropModel updater is established.

### Hose Spray stream-pose list

Constructor `004634F0` calls `00482850` on the pose subobject beginning at Hose `+0xC70`. The linked list's head, tail, and count are at Hose `+0xCB8`, `+0xCBC`, and `+0xCC0`; the current node cache is `+0xCD0`. Fresh construction creates 12 nodes through `00485D20` (the count setup uses `240/20`). The Training initializer path then resizes from the `touchhose 25` parameter through `00482780`; the source path supplies 30 (`25*24/20`, truncated by `004B9400`). `00485D20` allocates 0x30-byte nodes and links them in order; the first node is reachable at the list head. Its position is at `+8/+0xC/+0x10`; two three-float vectors occupy `+0x14..+0x28`. The constructor does not visibly initialize node `+0x2C`, so preserve that as unknown rather than defaulting it. `004827B0` separately writes pose defaults and does not resize the list. These counts and links are deterministic and this traced path contains no RNG draw.

## Native integration and remaining scope

`src/hose_item_selection.h` models the five Training slots, selected index, Axe child-state gate, mode change, slot-selection callbacks and detach rescan. `src/hose_attachment_frame.h` models the owner frame commit and its source-derived fixture inputs; the native Space/Shift path currently writes the exact authored valve position into the Hose pose and first node through `src/hose_spray_pose_list.h`. It does not yet apply the resolved valve-axis frame to the live Hose object; the fixture's Training residual axes still inherit the Java `Math` x87 substitution. The native pose-list check is source-derived, not an original allocation comparison. Hose follower parenting, post-view stream interpolation, UI/audio/stream/suppression effects, Axe busy-state cadence, recurring PropModel scheduling, cached-target schedule, and live view/candidate integration remain separate work. No live-game inventory capture has run. Player passout independently dispatches the selected slot's `+0x1C` ACTION-release method; Axe slot 1's release body is still unmapped, so `main.cpp` does not yet wire that path (`../fire-update/player-exposure-timer-followup/player-passout-transaction.md`).
