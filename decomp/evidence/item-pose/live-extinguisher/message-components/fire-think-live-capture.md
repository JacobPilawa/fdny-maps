## Bounded capture and recovery path

The recorder now takes `--max-seconds` (default 300), starts its wall deadline before process discovery, and reserves the final 30 seconds for recovery. Debugger prompts and continue waits share that deadline. It launches WineDbg at a prompt, submits the explicit hexadecimal `attach 0x<PID>` command, and requires an EIP/RIP register dump before treating attachment as successful. On timeout or error it interrupts a running target, confirms the prompt, issues `detach`, and exits WineDbg using the CR line ending required by this Wine console. It never sends a kill signal to the game. It warns rather than claiming success if detach cannot be confirmed.

The smoke test cloned the app's Wine prefix into a disposable temporary directory and used only Wine's bundled `ping.exe`. `info proc` found PID `0xC4`; `attach 0xC4` returned RIP; a forced two-second continue timeout was interrupted; `detach` and WineDbg exit were confirmed; and a second process listing showed the ping target still alive. The disposable prefix and target were then removed. The result is recorded in `result.json` with debugger and target transcripts. This validates command submission, bounded interruption, detach, and target survival for a harmless 64-bit process; it does not establish stability with the PE32 game, nor does it record Fire Think scheduling. Check-only mode still only hashes the installed executable and debugger. The next step is a live, user-driven main-menu-to-Training capture, with the same five-minute total cap.

## Evidence needed

The static Ghidra audits preserve `00449FE0` as slot 0 of FireRescue's visual secondary vtable `004E1774` at object `+0x24`; they do not identify its recurring caller. The bounded recorder observes the highest-value ordering points: Fire Think `00449FE0`, owner entry `00429520`, FireRescue primary influence callback `004483A0`, and mapped-message drain `0049B610`. The drain call is made by owner instruction `00429581` through service `owner+0x3BC`; the drain-entry event should return to `00429586`. Thus an observed `004483A0` event before `0049B610` within an owner pass confirms that callback's position before delivery. This is consistent with the static owner order and lets the dynamic trace verify the live receiver/caller path.

The same capture also observes player view `0044F340`, extinguisher post-view `00461F80`, Player message/exposure/damage callbacks `00453A70`/`00451640`/`00450FB0`, and shared RNG entries `00404AC0`, `00404B30`, `00498B30`, and `00404960`. Events preserve monotonically increasing sequence, registers, stack words, return address, receiver pointers and host monotonic time. The recorder also samples global game clock `00502AFC` at owner, Think, influence, drain, view and Player message/exposure/damage callbacks, allowing event order to be correlated with the game's own clock. The recorder does not capture RNG return values. Breakpoints pause the game, so observed order and caller identity are useful, but clock samples and host timestamps cannot establish normal-speed frame cadence. No frame counter has yet been mapped for this capture.

The Fire Think callback's caller, cadence and order remain unresolved. Do not connect `FireUpdate::think` or player exposure to the native tick until source-backed scheduling evidence supports it.
