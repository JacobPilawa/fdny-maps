# Fire Think live caller capture

The static Ghidra audits preserve `00449FE0` only as slot 0 of FireRescue's visual secondary vtable `004E1774` at object `+0x24`; they do not identify its recurring caller. `tools/record_fire_dispatch.py` is a bounded original-process capture for that missing edge.

Run `python3 tools/record_fire_dispatch.py --check-only` to verify the bundled Wine debugger and analyzed executable. To capture, leave the matching original game at its main menu and run `python3 tools/record_fire_dispatch.py`; enter Training manually. The tool verifies the executable hash and live entry bytes, then stops at Fire Think. After its first hit, it also records FireRescue primary callback `004483A0`, owner update `00429520`, player view `0044F340`, extinguisher post-view `00461F80`, mapped message drain `0049B610`, Player message handler `00453A70`, fire exposure callback `00451640`, damage-state callback `00450FB0`, and entries to shared RNG functions `00404AC0`, `00404B30`, `00498B30`, and `00404960`. Each event includes its return address, so `events.jsonl` preserves callback and RNG callsite order. For `004483A0`, the capture records the target object and the queued-exposure count at fire `+0xB8`; for Fire Think, it records that count through secondary-subobject `+0x94` immediately before Think resets it. Source limits the fire to four queued exposure records between resets. For message `0x7531`, it preserves the two payload words; exposure events preserve origin words, influence float bits, global clock and the pre-callback pain deadline. It detaches after 28 Fire Think calls by default; `--max-think-calls` changes that limit, and `--pid` selects a Wine process when more than one is running.

Each successful output under `evidence/live/fire-dispatch-*` contains a manifest, module list, debugger transcript and ordered JSONL events with return addresses, registers and stack words. Fire Think events also record the receiver vtable, expected to be `004E1774`. RNG entries show function entry/callsite order; they do not record the returned random value. The debugger does not send game input or write game memory. Breakpoints pause the process, so this capture can establish call identity/order but cannot establish normal-speed cadence. Both 2026-10-11 attempts (`evidence/live/fire-dispatch-20261011-074104-892169/` and `evidence/live/fire-dispatch-20261011-074723-753511/`) stalled on WineDbg's first interactive command before confirming any breakpoints. Neither contains gameplay events; the user observed a black/frozen screen after the first attempt and a crash after the second. Do not make another live attach until the command channel is independently validated. Do not connect `FireUpdate::think` or the player exposure path to the native tick until successful captured caller/order evidence supports it.
