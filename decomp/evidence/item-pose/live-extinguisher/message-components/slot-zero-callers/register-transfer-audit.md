# Expanded register-indirect transfer audit

Generated 2026-10-11 from the preserved read-only EXE and Genesis.dll Ghidra projects. This corrects the scope of the earlier zero-slot inventory: `slot-zero-indirect-calls.tsv` and `slot-zero-indirect-transfers.tsv` count memory-indirect forms such as `CALL [EAX]`; they do not include `CALL EAX` after a function pointer has been loaded into a register.

The expanded zero-offset sweep records 246 EXE transfers: 91 memory-indirect CALLs, one memory-indirect tail JMP, 152 bare-register CALLs, and two bare-register JMPs. The Genesis.dll sweep records 119: two memory-indirect CALLs, two memory-indirect tail JMPs, 113 bare-register CALLs, and two bare-register JMPs. The complete EXE inventory is `all-register-transfers.tsv`; `all-zero-offset-transfer-context-12.txt` preserves 12-instruction context for each site. The earlier 92 memory-indirect forms also have focused context in `slot-zero-memory-call-windows-12.txt`. Genesis inventory and register-call contexts are under `evidence/ghidra/genesis/`.

The 12 bare-register EXE sites without Ghidra function ownership were reviewed in focused assembly and decompilation. The address-based input router near `00429326` calls a supplied handler and a global callback for Windows mouse message values; `0042F0D6`/`0042F110` call a renderer-side function pointer; `00498D80` enumerates display modes; `004A9972` walks the runtime exit-callback array; `004C0329` walks a C++ destructor table; and `004C6524` invokes a global runtime callback. These paths do not dispatch Fire Think. Among the attributed in-game sites checked, `0046C480`/`0046C5A0` call a shared geometry API pointer and `004A2B9C`/`004A2C0B` use buffer allocator callbacks. The inventory is a candidate finder; it does not resolve the target provenance of every register-indirect call. Focused exports are in `register-call-candidates/`, `register-transfer-functions/`, and `register-transfer-candidates-final/`.

The inspected Genesis.dll register-indirect sites include pixel-format operations, driver callbacks, and compiler runtime initialization/termination tables. In particular, `10020AA0` calls the pixel-format operation selected by `gePixelFormat_GetOperations`, `10023950` enumerates graphics drivers and calls their `DriverHook`, and `10046847`/`100468AC` are runtime init/termination routines. The complete DLL inventory is preserved; this focused review does not expose an entity update loop that schedules FDNY FireRescue.

The 12-instruction memory-form contexts also show `0042E8A0`, a slot-0 dispatch inside `0042DEC0`. That function loads `menu.rrf` and constructs the menu's object arrays; this is startup/menu setup, not a recurring entity update.

Fire Think `00449FE0` remains slot 0 of FireRescue's visual secondary vtable `004E1774`, installed at object `+0x24`. Neither the earlier memory-indirect candidates nor the additional register-indirect sites reviewed here establish a recurring caller. The live caller and its order relative to player/tool updates and owner queue drain remain unresolved; this static audit does not prove there is no other dynamic dispatch path.

## Secondary-vtable field scan

A read-only headless `FindOffsetAccesses.java` scan of EXE offset `+0x24` produced 2,045 instruction rows in `../visual-secondary-scan/offset-24-accesses.tsv`. A function-level join against the 246 zero-offset CALL/JMP transfers in `all-register-transfers.tsv` found no recurring FireRescue visual dispatch. The apparent nested slot-0 path is `0042E896`–`0042E8A0`: `ESI` first supplies an object's primary vptr, then the code reads primary-vtable slot `+0x24` and calls its slot 0 while constructing menu objects in `0042DEC0`. It does not load FireRescue's secondary vptr from object `+0x24`. Other joined candidates are stream/runtime/API interfaces. This narrows the static candidates; register forwarding or a different update service may still hide the live caller.
