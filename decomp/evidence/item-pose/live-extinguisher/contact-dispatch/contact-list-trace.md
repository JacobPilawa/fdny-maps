# Extinguisher contact candidates

`00461F80` resets the 32-record contact collector, obtains an iterator from `00481C00`, and walks linked nodes. Each node stores an object pointer and next pointer. The routine checks candidate `+0x18 == 6`; each match is tested at four spray points with `0044A7A0(candidate +0x12c, point, 60)`. Influences at or above the original threshold are doubled and queued through `00481A60` / `0049D4E0` as message 30000.

## Candidate list

`00481C00` initializes an iterator; `00481BA0` resolves manager group `+0x54`, registers the cursor with `00481B00`, and starts at the linked-list head. The group is initialized by `0049C4E0` with mask 2. `00407BD0` returns each object’s flags from `+0x14`; the base constructor `0049D420` sets `0xFFEB`, and the FireRescue constructor keeps that value. `00429490` tests the flags against the group mask and inserts matches through the group vtable. Its insertion function, `0042B1A0`, appends nodes at the tail. Startup drains the factory queue FIFO and performs this registration before later entity passes, so the list order follows factory order and each class’s BSP input order.

The `+0x18` check is a separate type filter. `RCS_FireRescue` constructor `0044A330` sets it to 6; `RCS_WindowFire` constructor `004683F0` sets it to 7. The current Training BSP has seven `RCS_FireRescue` records (source IDs 162, 163, 165–169) and no `RCS_WindowFire` records. Their native routes 159–165 are derived from the saved factory order. This is source-derived list membership/order; no full original Training launch snapshot was captured. Initializer, dispatcher, and append instructions are preserved in `list-registration-assembly.txt`, `active-contact-call-path-assembly.txt`, and `evidence/entity-scheduler/`.

## Fire actor inputs

The tested actor is the FireRescue visual subobject at `+0x12c`. For Training’s point fires, `00448D60` initializes its world center at visual `+0x28` from the authored location and queues its initial size at `+0x88` as `{0.75 * H_Radius, 0.25 * H_Height, 0.75 * H_Radius}`. `0044AE80` advances the size keys into visual extents `+0x44/+0x48/+0x4c`. `0044A7A0` averages the X/Z extents, adds the 60-unit spray padding, doubles vertical displacement, and multiplies by alpha from the first flame sprite at `+0x60 + 0xD0`. Fire Think passes its strength-derived alpha through `0044A610`; `0047F1F0` writes the supplied value at sprite `+0xD0`. Floor alignment updates the visual transform before gameplay.

## Effect pool and conditional draws

The extinguisher constructor `00461690` initializes its pool at item `+0x3c8` through `00480260`. Setup `00461830` builds two type-14 effect descriptors at item `+0x3ac` and passes the pool, world pointer, and descriptor to `0047FE70`. That setup stores the world/config pointers, initializes pool word `+0x30` to `-1`, and registers the pool with the world when the flag is set. These exports are under `particle-pool/`; the call-site setup remains in `evidence/item-pose/live-extinguisher/00461830_FUN_00461830.c`.

When the fire-strength (`>= 0.05`) and timer gates pass, `00461F80` draws the timer range 10–250, adds the resulting x87 value to current game time, and converts it through `004B9400`. The captured fixture sets time 1000 and gets deadline 1134. It then asks `0047FF30` for an idle or newly allocated emitter. A returned emitter causes three more draws for offsets (`[-50,50]`, `[100,400]`, `[-50,50]`). The scalar words used by this path are preserved in `evidence/extinguisher-effect-thresholds.tsv`, exported by `tools/DumpScalarWords.java` from the read-only Ghidra project.

The source constructor `00480260` leaves the emitter array empty; setup `0047FE70` sets the maximum at pool `+0x30` to `-1`. `0047FF30` scans for an idle emitter, then allocates when that maximum is negative or the current count is below it. Thus a valid, newly constructed Training pool takes the allocation path on the first eligible effect request, assuming normal allocation succeeds, and returns an emitter. Later requests also can grow the pool if every existing emitter is busy. This statically establishes the source branch and its conditional draws, not the live frame’s contact/timer state or a rendered particle.

`tools/extinguisher_contact_path_oracle.py` captures two valid pool states. `evidence/extinguisher-contact-path-full-busy-pool-oracle.json` supplies a one-entry pool (maximum 1, count 1) whose emitter is busy; `0047FF30` returns null and the original observes 2 shared draws (active-pose prefix and timer). `evidence/extinguisher-contact-path-source-empty-pool-oracle.json` executes the original pool constructor/setup with an empty array and limit `-1`; a fixture descriptor lets the original allocator create one active emitter, and the original observes 5 draws, including all three emitter offsets. The source-empty capture uses a controlled one-frame descriptor, not the full authored Training descriptor state. Both valid captures record four contacts/messages and explicitly drain the original queue sequentially. Neither establishes callback order in a Training frame. Preserve but exclude the earlier files from parity claims: `evidence/extinguisher-contact-path-oracle.json` has the pool at a separate address instead of embedded item `+0x3c8`; `evidence/extinguisher-contact-path-disabled-pool-oracle.json` is byte-identical to that attempt; `evidence/extinguisher-contact-path-empty-pool-oracle.json` reports two draws and no pool result, so it does not demonstrate emitter allocation despite its provenance text. Raw pool constructors and setup are preserved under `particle-pool/`; allocator logic is in `particle-effects/0047ff30_FUN_0047ff30.c`.

`0049B4C0` appends a mapped record and linked queue node. `0049B610` drains the embedded queue at manager `+0x3bc`, subobject `+0x40`; the vtable at `004DF8CC` places it in slot 1. The owner update `0042AEA0` calls `00429520`, which dispatches that slot at `00429581` on the normal update path. This path is skipped by the owner’s early `+0x64c` branch.

The accepted message’s terminal flag is source-backed. Handler `00449A40` reads the contact's four words, then its assembly pushes `0` after the contact strength before calling `00448970`; the callee reads that byte as the terminal-particle flag. The native message delivery therefore applies nonterminal suppression. Extinguisher messages alone do not trigger final dousing or the doused statistic. Raw stack setup is preserved in `message-components/dispatch-assembly.txt`.

## Native message handler completion (2026-10-12)

`src/extinguisher_effects.h::deliverContact` now implements the bounded `00449A40` message decision shared by the fixture and live Training path. It accepts only message `30000`, reads contact strength from the fourth word of the preserved 16-byte record, and calls the target fire's `spray(dt, strength, false, ...)`. The false terminal argument comes from the raw handler stack setup noted above. Generation/route resolution remains in the queue owners; the live target remains `FireEntity::spray`, so entity-side visual effects continue to follow `FireSuppression::spray`. The fire-message checker uses a thin `NativeFire` adapter around the same suppression component; its former duplicate state-5 guard was redundant because `FireSuppression::spray` already returns for that state.

The edited header and all three call sites were built through `./run.sh --fire-message-check`; the message/registry oracle reported zero mismatches. `./build/fdny-training --extinguisher-contact-path-check` then compared 135 values across the two valid contact/effect-pool captures, also with zero mismatches. These checks close message selection and nonterminal delivery only. Original owner/frame drain order, recurring Fire Think, particle allocation/rendering, and whole-run Training parity remain open.
