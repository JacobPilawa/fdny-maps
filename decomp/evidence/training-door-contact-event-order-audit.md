# Training door contact-to-script event order audit

Read-only Ghidra 12.0.4 inspection of `FDNYFirefighter.exe` (SHA-256 `4b3b4dc1cc0b05bcb42c8e27ac6f6ca72fe5f7064ca8122fda7d41e7f6d2fc3e`) on 2026-10-11. The preserved project was queried with `-noanalysis -readOnly`; missing function boundaries were recovered only in the scratch project at `/private/tmp/fdny-bmodel-dispatch-scratch-20261011`. No live game capture or source-code changes were used.

## Verified local chain

The code proves these local edges and their order:

1. The normal owner manager path `0042AEA0 → 00429520 → manager +0xE0 → 0049BD20` calls BModel vtable slot `+0x48` (`0043B620`) to build the current contact-pair list. This is per normal owner-manager pass; its cadence is unknown. See [`training-bmodel-contact-scheduling-audit.md`](training-bmodel-contact-scheduling-audit.md).
2. The BModel ScriptActor update path is primary vtable slot `+0x14` at `004E0E0C → 0043AFE0 → 00470740`. The thunk adjusts `this` to the ScriptActor subobject at root `+0x24`. If the wait flag at subobject `+0x4C` is 1 on entry, the shared updater checks deadline `+0x48` against game clock `00502AFC` and skips the virtual callback for that invocation, even if that check clears the flag. If the wait flag is clear on entry, it synchronously calls subobject vtable slot 0, installed as `0043DC60` from `004E0DF0` by constructor `0043F340`. Thus `0043DC60` is the local callback that drains BModel contacts, but this edge does not identify who schedules root slot `+0x14`.
3. In `0043DC60`, call `00470840` at `0043DD74` converts pair snapshots in order: new current pairs emit `touch`, all current pairs emit `touching`, then previous-only pairs emit `untouch`. Event lookup/dispatch proceeds through `00470B50 → 004705B0`; command dispatch reaches `00470150`. After the drain returns, current pairs are copied to previous at `0043DED9` and the current count is cleared at `0043DEE0`.
4. After contact conversion, the same `0043DC60` invocation continues into BModel motion/time handling and Genesis path sampling. Consequently, when a Training `touch` event dispatches the authored `DoorOpen` macro in this callback, its `cmd [flush, openaway, playsnd]` children run synchronously before this callback's later motion step. `openaway` can therefore modify the door's path/state before that same callback samples the motion path. This is only the order *within one `0043DC60` invocation*; it does not establish which owner pass generated the pair or when this invocation occurs.
5. Training's `untouch` macro is `DoorClose = (que [close, playsnd CloseDoor])`. `que` appends rather than dispatching inline. When `0043DC60` returns to `00470740`, the updater invokes `004704A0` if the wait flag is clear; `004704A0` removes and dispatches at most one queue item. Therefore, if the callback returns with wait flag clear, the first queued `close` is eligible for dispatch after the callback returns within that same `00470740` invocation. This conditional local ordering is source-backed; later queue items are subject to subsequent callback/state behavior.

The Training macro source is [`original/doors.evs`](original/doors.evs); ScriptActor queue semantics are also detailed in [`training-script-queue-audit.md`](training-script-queue-audit.md). The `touch`/`untouch` comparisons and producer path are documented in [`training-bmodel-contact-scheduling-audit.md`](training-bmodel-contact-scheduling-audit.md).

## Still unresolved

Ghidra xrefs show `0043DC60` only as the ScriptActor vtable word `004E0DF0`; they do not reveal the dynamic caller that invokes BModel root slot `+0x14`. The owner manager pass dispatches BModel slot `+0x48`, not `+0x14`; the inspected staging and render paths do not close this gap. The ordering of the contact producer (`0049BD20`/`0043B620`) relative to the ScriptActor updater (`0043AFE0`/`00470740`) is therefore unknown. We cannot say whether a newly produced pair becomes `touch` in that same owner pass or a later updater callback, nor assign a rendered-frame or wall-clock latency. The call chain proves local event ordering, not the complete Training door schedule.

## Bounded scheduler-caller sweep

A follow-up read-only sweep did not establish a caller of the BModel root slot `+0x14`. Address xrefs for `0043AFE0` return only data references from vtable words `004E0E0C`, `004E10A4`, and `004E1794`; there is no direct code xref. `0043DC60` has only its vtable data reference at `004E0DF0`. The known BModel owner/contact function `0049BD20` invokes slot `+0x48` (`0043B620`), not slot `+0x14`.

The direct-call graph query to shared updater `00470740` from `0042AEA0`, `00429520`, and `0049BD20` found no direct path. Those traversals visited 514, 167, and 152 functions respectively, but stopped at 292, 145, and 141 indirect call sites; this is not evidence that no dynamic caller exists. A listing sweep also enumerated literal `CALL [register + 0x14]` forms as candidates, but that syntax scan cannot resolve a receiver passed through an earlier load, another register, or a nonliteral dispatch sequence.

The closest examined candidate is `00459519` in Player use-candidate scan `00459350`, reached from `00459630`. At `004594C1–004594D1` the function loads a candidate from the array at `+0x188`, calls that candidate's slot 0, and receives `local_7C`; at `00459519` it calls the returned object's slot `+0x14` with query/vector arguments, then tests `AL` at `0045951C`. Existing [PropModel use-manager evidence](hose-spray/README.md) identifies ordinary Training PropModel candidates and their interaction-sphere query in this path. However, the provider-list construction and dynamic type of every returned `local_7C` are not proven by this bounded check, so it does not prove that this receiver can or cannot be a BModel root. Its arguments and boolean result differ from the known no-argument BModel updater thunk, but that signature difference alone is not a safe exclusion. The candidate therefore does not identify the updater scheduler.

The conclusion remains limited: the regular owner/contact, staging, render, and examined Player selection paths do not establish the caller. The BModel root `+0x14` caller and its order relative to contact-pair production remain unknown. No broader claim about all virtual-dispatch paths is supported.
