# Training liftable objects and BModel USE route

This audit combines read-only Ghidra queries on `FDNYFirefighter.exe` with the serialized Training BSP typedef, extracted Training entities, and model motions. No live gameplay capture was used. Function names are provisional; claims below identify addresses and the fields/branches observed.

## Authored objects and motion data

The raw BSP typedef is preserved in `evidence/bsp-typedefs/training-bmodel.json` (source SHA-256 `32986212fa875764ca3d5c1630e54ad6315abaea70983203601192cec603a963`). It contains 26 fields and 112 bytes. In particular `E_Reach` is float at `+0x30`, `F_HitPoints` is int at `+0x34`, and `G_Liftable` is int at `+0x38`. Re-running `tools/extract_gbsp_typedefs.py` against the supplied retail `training.bsp` reproduced this JSON byte-for-byte.

## BModel lift state and Player pointer

The BModel constructor `0043F340` installs the secondary vtable at root `+0xA0`; Ghidra data words at `004E0DE4/004E0DE8` identify its first two slots as `0043DB40` and `0043D2B0`. The constructor also creates a separate axis-box interface at root `+0x260` with vtable `004E0CBC`.

Initialization sets BModel `+0x258` to 2, checks UserData `+0x38`, and invokes `0043BE00` when nonzero. That routine obtains model motion path 0, requires exactly two keyframes, and validates times 0 and 1 through `0043B120`. On success it stores the two endpoint vectors and writes 1 to BModel `+0x258`. The Training typedef proves UserData `+0x38` is `G_Liftable`; entities 109 and 111 set it to 1. The meaning of the intermediate value 2 is unknown.

The vtable slot-0 method `0043DB40` reads the BModel status at receiver `+0x1B8` (root `+0x258`). Status zero logs an invalid `TE_BModel::useMode` and returns zero. For a nonzero status it supplies the axis-box interface at root `+0x260`; status 1 asks Player method `0044C520` for an action code, while other nonzero values return code 1000.

`0044C520` offers action code `0x3EC` (1004) only when Player item-array slot 4 (Hose Spray) is absent or its object field `+0xC68` is not 3, Player byte `+0x12C` is nonzero, Player held-object pointer `+0x3440` is null, and the BModel object state at `+0x25C` is zero. Eight controlled executions of original `0044C520` compare the returned action; no live values were captured, and the meaning/lifecycle of byte `+0x12C` remains unknown. Do not confuse it with the `+0x12C` write in `00459630`: that callback receives `Player+0x3114`, so its write is actually `Player+0x3240`. The BModel's slot-1 handler `0043D2B0` reacts to status 1 by calling `0044BC40(player, BModel root)`, then forwards a `use` event to the BModel script component at root `+0x24`. `0044BC40` stores the object at Player `+0x3440`, sets BModel `+0x25C` to 1, calls `004571A0(Player+0x5F4, 3, nullptr)`, then enters Player state 7. One controlled P-code transition execution intercepts that helper, confirming its receiver/arguments and ordering but not its service effects. The Player updater `00452570` uses this pointer for held-object positioning and later release. The exact throw branch is now source-mapped: its gate is angular separation strictly below 10 degrees; the throw duration is distance/960 seconds with vertical acceleration -384. Its static subobject method `0043DC60` calls updater `0043D330`; the dynamic dispatcher and update cadence are unresolved. See `training-liftable-audit/bmodel-use-component.md`, `training-liftable-audit/throw-path-ghidra-audit.md`, [`training-liftable-audit/throw-scalar-oracle.md`](training-liftable-audit/throw-scalar-oracle.md), and [`training-liftable-audit/throw-runtime-ghidra-audit.md`](training-liftable-audit/throw-runtime-ghidra-audit.md).

## Candidate selection and geometric query

Player routine `00459350` scans its candidate array, calls each candidate's vtable slot 0 for an action code, and when a geometric-query interface is returned calls its vtable slot `+0x14`. It accepts a hit within the squared 200-unit limit and replaces an equal-scoring current candidate, so later candidates win ties. `00458FA0` dispatches the selected candidate's vtable slot `+4` with the stored action code.

For BModels, the returned root `+0x260` axis-box interface has its query method at vtable address `004E0CD0`, which points to `00489D80`. That method calls `00482B90` with the query ray and axis-box bounds at interface offsets `+0x18/+0x24`; it returns a hit point and score `1.0` on success. The generic BModel vtable values and these function targets were read from the preserved Ghidra project. The Ghidra p-code oracle contains 268 queries. Its nine signed-zero boundary cases are explicitly annotated and excluded from the native comparison because EmulatorHelper leaves a stale x87 condition bit; the native check compares the remaining 1,813 outputs. The three former point-only ULP differences were fixed by retaining the extended-precision normalization reciprocal through component multiplication. Negative-zero far-output parity is still unresolved. This diagnostic query is not yet integrated. The p-code exclusions and instruction-level trace are documented in [`bmodel-interaction-box-oracle-audit.md`](bmodel-interaction-box-oracle-audit.md). The saved project lacked function boundaries at `0043DB40` and `00489D80`; those entries were defined and decompiled only in a temporary copy under `/private/tmp`, leaving the user-open Ghidra project unchanged.

## Native status and remaining verification

The native BModel touch path now applies the source-derived conditional 48-unit override. The exact predicate and Training outcomes are recorded in `training-bmodel-contact-audit.md`: entities 113, 212, and 213 use 48; entity 112 retains authored reach 50 because the source requires a strict reach below 48. This does not complete contact scheduling or event parity. Native BModel candidates in USE selection, state 7 carry/throw, and original candidate array order remain unimplemented. The generic axis-box ray query, exact selected-item conditions, Player `+0x12C` meaning, model-transform integration, and live input-to-event schedule remain open. The isolated native scalar throw helper matches 24 setup fields and 64 update branch/point fields against the Ghidra p-code fixture; this does not establish renderer/model parity, gameplay integration, hardware parity, or runtime cadence (`training-liftable-audit/throw-scalar-oracle.md`, `training-liftable-audit/throw-scalar-native-check.md`). Static Ghidra maps the direct subobject method and model mutator, but runtime dispatch cadence remains unknown (`training-liftable-audit/throw-runtime-ghidra-audit.md`). The 1004 handler route is source-backed; its Training execution has not been observed live.
