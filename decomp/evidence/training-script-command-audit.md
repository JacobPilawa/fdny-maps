# Training script command audit

Static command audit recorded 2026-10-11 against the read-only Ghidra 12.0.4 project for `FDNYFirefighter.exe` (SHA-256 `4b3b4dc1cc0b05bcb42c8e27ac6f6ca72fe5f7064ca8122fda7d41e7f6d2fc3e`). The authored entity/script inputs are `assets/training/entities.json` and `assets/training/scripts.json`. No live gameplay capture was used.

## Command host status

| Command | Training input and original evidence | Native status and limit |
|---|---|---|
| `makezone` | Five `RCS_BoundsTrigger` entities (114, 135, 158, 190, 234) create the five named Training exercise zones. Ghidra traces `00441040 → 00475310 → 00470150 → trigger vtable +4 (00441A60, scratch-defined) → 004418E0 → 00484740`. The zone manager groups trigger boxes by case-sensitive label, sums member-box volumes, and indexes eligible actors by containing zone; see [`training-zones-runtime-audit.md`](training-zones-runtime-audit.md). Exact box construction and the generic `C_Model`-to-runtime pointer handoff are in [`training-zone-bounds-ghidra-audit.md`](training-zone-bounds-ghidra-audit.md); mapping each Training entity ID to its specific runtime instance and actor update cadence remain open. | Native startup builds the five named groups; `src/zones.h` implements source-ordered inclusive lookup and summed-volume selection. `--training-zone-check` validates all five labels/bounds and boundary lookups. Actor membership, gameplay consumers and exit-zone evaluation remain unimplemented. |
| `makevalve` | PropModel handler `004444B0` writes `1` to its instance flag at `+0xEC`. Training PropModels 159 and 164 use it; the source query path `004442B0 → 0044C780` uses the valve instance state to offer attach/detach actions. | The native `TrainingPropModel::makeValve` and valve-candidate list are already derived from the exact authored `S_Script01=makevalve` property, so the Training use gate is represented outside the host callback. The native callback itself remains a no-op. |
| `setscale` | PropModel handler `004444B0` parses three floats and calls `004437C0`; that routine composes the scale through `0042D280` into the PropModel transform. Training entity 161 (`ext1`) authors `0.2 0.2 0.2`. | Native PropModel transforms/presentation are not implemented, so storing this value alone would have no visible effect. |
| `settimescale` | BModel handler `0043E680` parses a float and writes receiver `+0x1B8` (BModel base `+0x1DC`). The shared `Door` macro uses `3.0`; its use is bound on Training's authored doors. (`settimescale 500` also appears in the reusable `GrabAxe` definition, which no Training entity references.) | Native approach doors hard-code the authored value 3 in their update. General BModel motion/time scheduling is not ported or compared. |
| `sethitpoints` | `0043E680` parses an integer and writes the BModel data pointer's `+0x34` field (`0043E9B0–0043E9DB`; handler receiver `+0xC8` maps to BModel base `+0xEC`). Training's shared `Door` macro and each matching entity set it to 0. | Ghidra shows the axe-hit reader `0043E2A0` returns before chop processing when this field is zero; on positive hitpoints it decrements and dispatches `break` at zero. The axe caller is `00460B90` (`0046102B`). This establishes that Training doors cannot be chopped/broken through this path. It does not show that hitpoints affect ordinary door motion, and native axe mechanics remain unimplemented. |
| `openaway` | `0043E680` calls `0043D6A0` for each BModel. The routine may queue its `openaway` event when state `+0x70` is 4; otherwise it derives a direction from the authored two-keyframe motion path and player position, may modify keyframe 1, then writes state 3. Training's `DoorOpen` macro invokes it. See [`training-door-motion-audit.md`](training-door-motion-audit.md). | Native `Door::update` approximates proximity opening and direction, but original EVS event timing and exact model-motion composition are not verified. |
| `close` | `0043E680` calls `0043DA70`. If state `+0x70` is not 3, it writes state 4. If it is 3, it clears the ScriptActor queue/wait and appends a `close` event without directly changing the state. Training's `DoorClose` macro invokes it. See [`training-door-motion-audit.md`](training-door-motion-audit.md). | Native doors reverse their local fraction when the player leaves; the original state/queue path is not implemented or compared. |
| `flush` | Handler `0046F9D0` calls `0043B6E0(this+0x30, 0)` when the embedded container count at `+0x34` is nonzero, then writes zero to `+0x4C`. Ghidra shows `0043B6E0` shrinking a pointer container: it calls the stored release callback for each non-null removed entry, resets the allocation size to zero, and stores the new count. Training's `DoorOpen` macro runs it before `openaway`. | Container entry types and callback meaning remain unresolved; native `Door` has no equivalent script subobject/state to update. Local raw decompilations: `evidence/startup-factories/0046f9d0_FUN_0046f9d0.c` and `evidence/startup-sound/0043b6e0_FUN_0043b6e0.c`. |
| `setrescuebot` | Player command handler `00451870` parses with `0040CD50` (`sscanf` `%i`) and stores the nonzero result at Player `+0x32E4`. Training Player entity 115 authors `setrescuebot 0`; native first-pass script dispatch is ordered through the verified startup queue. | Implemented as an optional source-backed Player setting; Training resolves it to `off`. No RescueBot behavior is being inferred or connected. |

## Other reachable gaps

- Training exit triggers issue `tell player escape`. The source path is `00451870 → 004513A0 → 00451160`, and victim pickup/release helpers are traced in `evidence/victim-ai-audit/training-pickup-flow.md`. The native host does not implement `escape`; carry state and victim updater schedule are also unresolved, so it is not safe to wire an apparent rescue based only on trigger proximity.
- Training authors breakable furniture and axe hints in the chopping exercise. The loaded `GrabAxe` macro is defined in `Scripts/tools.evs`, but no Training entity references it; keep that generic break handler as a full-game lead. The native host does not provide the original sound service or axe mechanics.
- The Player handler also contains `finalexit` and `finalexitloadmap`, but no such command appears in the extracted Training input. They remain whole-game leads rather than Training requirements.

- ScriptActor `que`/`wait`/`flush` behavior and native limits are recorded in `evidence/training-script-queue-audit.md`. The local native update hook is not a verified original callback schedule.

## Verification limits

The command stores and call edges above were checked in Ghidra. No focused runtime oracle exists for these script-level actions. The previous WineDbg attempts did not produce gameplay events, and this audit did not retry live capture. Door motion and mission-zone timing therefore remain open. `makezone` grouping and point lookup are implemented from the source trace, but actor membership/update schedule and exit evaluation are not. The explicit `setrescuebot` setting write is covered by `--script-check`; Training's value is statically known to be false.
