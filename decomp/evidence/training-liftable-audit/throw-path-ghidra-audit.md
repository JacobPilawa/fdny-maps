# Training liftable throw path: Ghidra audit

Read-only Ghidra 12.0.4 audit of the preserved `FDNYFirefighter.exe` project, with function-boundary recovery only in a scratch project under `/private/tmp`. Training schema/data references are from `evidence/original/training.bsp` and its extracted layout at `evidence/bsp-typedefs/training-bmodel.json`. No live-game interaction or native source edits were performed.

## BModel `useMode` and the `G_Liftable` field

- BModel construction `0043F340` obtains a `0x70`-byte UserData block at object `+0xEC` through `0049D160`. The class-registration routine at `0043B4B0` passes the name `RCS_BModel` and value `100` to `0049B690`. The executable contains the `RCS_BModel` string at `004E0BA8`; `FindStringReferences.java` found no native `G_Liftable` string/reference.
- The embedded Training `RCS_BModel` typedef has 26 fields in a 112-byte (`0x70`) layout. Its `G_Liftable` integer is at byte offset `0x38`; this is recorded in `evidence/bsp-typedefs/training-bmodel.json` and reproduced from the preserved Training BSP. Native code at `0043D273` reads the BModel UserData pointer (`object+0xEC`) and tests `[UserData+0x38]` before calling lift initializer `0043BE00`. The schema name and native offset test therefore agree. I found no separate native property-name registration that names `G_Liftable`.
- Base initialization at `0043C6A0` writes zero to BModel `+0x258`. The later initialization path at `0043D273` writes 2, then checks UserData `+0x38`; on successful two-keyframe validation `0043BE00` writes 1 at `0043C0F5`. The BModel secondary vtable slot 0 is `0043DB40` (pointer at `004E0DE4`). It treats receiver `+0x1B8` as `useMode` (BModel root `+0x258`): mode 0 logs `TE_BModel::useMode is invalid` and returns 0; nonzero mode supplies the axis-box interface at root `+0x260`; mode 1 calls Player method `0044C520`; any other nonzero mode returns 1000. Slot 1 at `0043D2B0` is referenced from vtable word `004E0DE8`: it calls `0044BC40` only when mode equals 1, then forwards a `use` event to the ScriptActor subobject at root `+0x24`.
- `0044BC40` stores the object pointer at Player root `+0x3440`, writes object `+0x25C=1`, and sets Player state `+0x18C=7`. This verifies mode 1 as the carried/liftable route. The intended higher-level meaning of mode 2 and the semantics of returned action value 1000 are not established here.

## Training objects covered by this path

The extracted records from the preserved Training BSP identify entity 109 as `obj_liftable_metalbox` (model 7) and entity 111 as `obj_liftable_metalbox1` (model 8). Both records set `G_Liftable=1`; their models have two translation and rotation keys in `assets/training/motions.json`, at times 0 and 1, matching the shape required by `0043BE00`. Entity 109's `S_Script01` is `touch: hint 2 (Press SPACE to clear this object from your path.)`; entity 111's corresponding field is empty. These records satisfy the static schema/motion prerequisites for the native lift-mode initialization; actual in-game reach/use timing has not been captured.

## Player release condition

The preserved database has no function boundary at `00452570`; a function was defined and decompiled in the scratch project. Its updater parameter is the Player subobject at root `+0x140`, so updater `+0x3300` is Player root `+0x3440`, and updater `+0x4C` is Player root `+0x18C`.

- The held-object block in `00452570` is guarded by `Player+0x3440 != 0`. There is no explicit `state == 7` comparison at this block; the setter `0044BC40` writes state 7 and the held pointer together. Before the release test, the updater derives an object position from the Player transform, writes it into the held BModel's position fields, and calls `0043BD90`.
- At callsite `00453964`, helper `00497AA0` computes the angle between two vectors: a vector formed from the held object's selected endpoint and updater field `+0x338C`, and the three-component vector copied from updater field `+0x3364` by `0049E770`. (`00452570`'s updater parameter is the Player subobject at root `+0x140`, so these offsets are relative to that subobject.) The exact semantic labels for these vectors are not established by this audit.
- `00497AA0` forms `dot(A,B) / (|A||B|)`, calls `004B96E0`/`004B96FD` (the latter evaluates `atan2(sqrt((1-x)(1+x)),x)`, equivalent to `acos(x)` for in-range cosine), then multiplies by the double at `004E2330`. The executable bytes at that address are `F8 C1 63 1A DC A5 4C 40`, or `180/π`; the helper output is angular separation in degrees. There is no explicit cosine clamp in `00497AA0`.
- `00452570` compares the result with float `10.0` at `004E169C`. At `angle >= 10°`, it takes a side-selection branch (`004476B0`) and assigns status 1 or 2. At `angle < 10°`, it calls `0043B580`, sends status 4 through `004571A0`, clears Player `+0x3440`, sets state `+0x18C` to 3, and increments `Objects Thrown`. This is an angle gate, not a timer threshold or a direct input test.

## Throw trajectory and update dependency

- Lift initialization `0043BE00` stores the two validated motion endpoints at BModel `+0x1F0..+0x1F8` and `+0x1FC..+0x204`; it checks the two keyframe times against 0 and 1 through tolerance helper `0043B120` (called twice from `0043BE00` with tolerance parameter 2).
- Throw setup `0043B580` snapshots global tick `DAT_00502AFC` to `+0x208`; stores `-384.0f` at `+0x210`; copies the starting middle coordinate (`+0x1F4`) to `+0x218`; and sets object mode `+0x25C=2`. It stores `+0x20C = length(start-end) * 0.00104166672f` (`004E0BB8`, rounded `1/960`) and `+0x214 = ((endMiddle-startMiddle) - duration² * (-384.0f)) / duration`.
- Update handler `0043D330` checks object mode `+0x25C`, computes elapsed time from `DAT_00502AFC - +0x208`, and compares the scaled value with `+0x20C`. Its negative-delta branch adds `4294967296.0` from `004DFC90`, then it multiplies by `0.001` from `004DFA28`; these constants establish a 32-bit millisecond counter with rollover handling and seconds for the elapsed value. Thus `+0x20C` is a duration in seconds, and its setup formula is distance divided by 960 per second in game-coordinate units. While active, the handler linearly interpolates the first and third endpoint components and computes the middle component as `(t * -384 + +0x214) * t + +0x218`; it then applies the position through `0043BAA0` and updates the model transform. On completion it sets mode 0, selects an endpoint, flips the endpoint selector at `+0x220`, sends the `drop` event, and clears the timer object at `+0x124`.
- `AddressXrefs.java 0043D330` found a single direct call at `0043DDC6`, in code without a saved function boundary. This audit did not identify the caller's scheduler or prove a per-frame cadence. The elapsed counter and duration scaling are source-backed, but scheduler cadence and the original caller's event order remain unresolved.
